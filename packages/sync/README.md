# @dotlife/sync

قاعده‌های همگام‌سازی (PLAN §9، قدم ۱۶.۲)، خالص و مشترک بین اپ و سرور. بدون شبکه، بدون دیتابیس.

- **تغییر (`Change`)** = کل رکورد همان‌طور که الان هست (`data`)، یا `null` وقتی برای همیشه حذف شده (حذف نرم، مثل `deletedAt` کار، داده‌ی معمولی است). `changedAt` = لحظه‌ای که گوشی تغییر را داد، نه `updatedAt` خود رکورد.
- **قاعده (v1):** تغییر دیرتر برنده است، کل رکورد. در تساوی: حذف، بعد JSON بزرگ‌تر — هر طرف با همین دو نسخه همان تصمیم را می‌گیرد، پس ترتیب رسیدن تغییرها مهم نیست (`supersedes`). ادغام فیلدبه‌فیلد (مثلاً دو گوشی روی دو نوبت یک کار تکراری) برای نسخه‌های بعد.
- **ساعت گوشی:** مهری بیش از ۵ دقیقه جلوتر از سرور، «همین الان» حساب می‌شود (`clampClock`)؛ وگرنه گوشیِ ساعت‌جلو تا آن زمان همه‌ی ویرایش‌های دیگران را می‌برد.
- **سرور:** `acceptPush` (هر تغییر برنده با `rev` بعدی نوشته می‌شود، بازنده‌ها با نسخه‌ی سرور برمی‌گردند) و `pullPage` (رکوردهای عوض‌شده بعد از cursor، یک نسخه برای هر رکورد).
- **گوشی:** `applyPull` (نسخه‌ی سرور جای نسخه‌ی محلی، مگر تغییر ارسال‌نشده‌ی محلی دیرتر باشد) و `settlePush` (کدام ردیف‌های outbox تمام شدند؛ رکوردی که وسط ارسال دوباره عوض شده می‌ماند).
- **قالب سیم:** `PushRequestSchema`، `PushResponseSchema`، `PullResponseSchema` (Zod)؛ حداکثر ۲۵۶KB برای هر رکورد، ۵۰۰ تغییر در هر push/pull.

`test/simulate.test.ts` چند گوشی (با ساعت درست، عقب، و ۴۰ دقیقه جلو) و یک سرور را با ویرایش‌ها و همگام‌سازی‌های تصادفی اجرا می‌کند و چک می‌کند همه به یک حالت برسند.
